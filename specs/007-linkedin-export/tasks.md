# Tasks: LinkedIn Export

is between the tool and the surrounding wiring, not within the tool.

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (US1–US4)

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies. T001 and T002 touch different files and can run together.
- **Foundational (Phase 2)**: Blocks every user story. T003 → T004 → T005 are sequential (same file, each builds on the previous).
- **US1 (Phase 3)**: Depends on Phase 2. T006 (authored files) is `[P]` — a content file, independent of the tool. T007–T014 are sequential within `tools/build-linkedin.ts`.
- **US3 (Phase 4)**: Depends on US1's T011 (the Experience block it nests into).
- **US2 (Phase 5)**: Depends on US1 and US3 — counts must measure the finished blocks.
- **US4 (Phase 6)**: Depends on US1's T006/T007; hardens what they establish.
- **Polish (Phase 7)**: Depends on all of the above.

### Story Independence

US1 is the MVP and stands alone. US3, US2 and US4 each add a distinct guarantee on top of it and are
individually verifiable, but because they all edit one file they are best done in the order above
rather than in parallel.

### Parallel Opportunities

- T001 and T002 (Phase 1).
- T006 (authored copy) alongside any Phase 2 task.
- T025 and T026 (Phase 7).

## Implementation Strategy

### MVP (User Story 1)

1. Phase 1 → Phase 2 → Phase 3.
2. Run `npm run content:check && npm run linkedin:build`.
3. Validate with [quickstart V1](quickstart.md#v1--both-languages-complete-structure-us1). At this point the files are already usable for pasting — they are simply missing assignment bullets, counts and diagnostics.

### Incremental delivery

1. MVP as above.
2. + US3 → assignments nested correctly → validate V3.
3. + US2 → counts and warnings → validate V2.
4. + US4 → strict authored-copy handling → validate V4.
5. Polish → docs, typecheck, full quickstart run.

## Implementation record (2026-09-07)

All 27 tasks complete. Three decisions were taken during implementation and cascaded back into the
design artifacts rather than left in the code alone:

- **Skills ordering** — `years`-based ranking produced `Linux, SVN, C, …` and pushed Terraform,
  NestJS and Next.js out of the 50-item cap. Replaced with CV order (newest entry first, authored
  order within an entry). Recorded as [R8](research.md#r8-ordering-the-skills-list); `data-model.md`
  and T013/T017 updated.
- **Position title** — `meta.txt`'s `Role` is English-only, so the Swedish file read
  `Title: Consultant`. Switched to the per-language entry `title`, with `(CV role: …)` appended when
  the two differ. Recorded as [R9](research.md#r9-which-field-becomes-linkedins-position-title).
- **Assignment bullet label** — includes the assignment title, and omits the client for in-house
  work where it would only repeat the employer.

Counts differ from the initial estimates: the CV holds **16** employment entries (the second Teleca
entry, `200702_Teleca_summary`, was missed in the first count) and **34** assignments. No block
currently exceeds a LinkedIn limit — the largest, Connected Table, is ~1 700 of 2 000 characters —
so `quickstart.md` V2 now describes how to exercise the over-limit path deliberately, and V5/V6 were
rewritten to avoid `npm run clean`, which would delete the dated PDF/DOCX files the deployed `out/`
references.
